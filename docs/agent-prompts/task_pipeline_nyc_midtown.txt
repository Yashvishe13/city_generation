Write the complete OpenStreetMap -> Unreal pipeline for one area: nyc_midtown
(Midtown Manhattan, bbox south=40.7500 west=-73.9860 north=40.7555 east=-73.9790; the
preset is in data/areas.json).

FIRST load these skills, in this order. They define what you are writing and what you
are writing it against, and none of them is discoverable - you must load them by name:

  osm:pipeline-plan     how to proceed, what to measure, what has gone wrong before
  osm:pipeline-shape    what the artifact must be: one file, no absolute paths, real checks
  osm:scene-contract    what Unreal reads, and the rules that break the build if ignored
  osm:coordinates       how to project lon/lat into Unreal's frame, and how to prove it
  osm:fetching          how to download the area yourself, and cache it
  osm:inspection        what to measure about the area before interpreting it
  osm:roads             cross-section width, the pedestrian realm, junctions
  osm:ground-cover      water, parks, landuse, and the Z stack they sit in
  osm:estimation        how to derive what OSM does not state, without inventing it

There is no tool that fetches, lists, measures or runs anything. You write the fetch and
you write the analysis, as the first two stages of your own pipeline. The one tool is
osm_verify_scene, for checking what you produced.

Write agent_scripts/nyc_midtown/PLAN.md first, then agent_scripts/nyc_midtown/pipeline.py:
- Python 3, standard library ONLY (pyproj, shapely, numpy are not installed).
- SELF-CONTAINED end to end: fetching from Overpass through to
  data/ue/nyc_midtown/scene.json. Running the file alone, on a clean checkout with an
  empty data/raw, must do the whole job. Cache the download so a re-run does not re-hit
  the API.
- CLI: --area (default nyc_midtown), --repo, --force, --verify. --repo must be honoured.
- NO absolute path anywhere in the file or in anything it writes. Derive the repo root
  from --repo / CITYGEN_REPO / __file__. Provenance recorded in scene.json is
  repo-relative. A pipeline that only runs from one checkout is a failed run.
- Deterministic: same input -> byte-identical output.

It must handle, because this area contains all of it:
- building:part volumes overlapping their parent outlines - extruding both double-builds
  every tower;
- roof:shape / roof:height, where roof height is contained in the total height;
- parts that start above ground (min_height / building:min_level);
- roads with NO width tag anywhere in this area;
- buildings stating neither height nor levels.

Report your emitted extent next to the requested bbox. Last run it was 1438 x 1567 m for a
611 x 591 m request, and the cause was three below-grade features extruded at street
level - Grand Central Terminal, Times Square-42nd St and 34th St-Herald Square, all tagged
building=train_station with location=underground and layer<0, up to 737 m across. Apply the
same layer/tunnel/location test to buildings that you apply to highways and railways.

Ground cover is not in the default selectors and must be added: leisure, landuse,
natural, water, waterway, railway. The cached extract in data/raw predates those
selectors - it holds 1 leisure and 2 landuse features and no water or railway at all - so
this run MUST re-fetch. Key the cache on the query (selectors, bbox, buffer, date), not on
whether the file exists, or a widened selector list silently returns the old narrow data. In this bbox that is ~303 elements, mostly Bryant
Park's gardens and fountains, plus 58 railway=subway ways that are BELOW GRADE and must
be excluded like the indoor footways. Give every flat class its own Z. The engine's
ground slab is appended with Origin=Base at Z=-100, so its TOP is at Z=0 - that is the
ground, and the carriageway sits 4 cm above it. Ground cover goes in the band between
them; anything below zero is inside the slab and renders as nothing.

The street network is half the result and the half that has been under-built here twice.
This extract states far more about its streets than `lanes`: sidewalk:*, oneway,
cycleway:left/right, lanes:bus, parking:left/right, turn:lanes, surface, maxspeed, name.
1062 of 1245 highway features are non-driveable and they are NOT one thing - 453 mapped
sidewalks, 241 crossings, 59 plaza polygons, 117 steps, and 93 indoor/tunnel/below-grade
ways that must stay out. 102 of 174 driveable endpoints are shared, so there are ~100
junctions to resolve rather than ignore. Read osm:roads before writing any of it, and
report each subset you emitted or excluded with its count and reason.

Constants fitted from THIS area's data are correct and expected - this pipeline is for
Midtown. What is not acceptable is a number with no stated origin. Every derived value
carries its provenance, and the manifest lists every assumption the run actually used.
After parsing, print the provenance histogram and compare it against the tag coverage you
measured: this area states height on ~84% of buildings, so a manifest that shows almost
everything falling to a default means your parser is reading tags from the wrong level,
not that the data is poor.

When the scene is written, run your own --verify checks (they must be able to fail), then
call osm_verify_scene and fix what it reports, then run it again. It checks your output
against the original OSM extract, not against your own manifest, so it will catch a
projection or orientation mistake that looks fine from inside your own code.

Report: what the analysis told you about the area, what you fitted and from what sample,
what you estimated and how you validated it, what the verifier said, and confirmation
that a second run is byte-identical.
